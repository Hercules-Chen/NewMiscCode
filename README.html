快速開始

1. 先裝好的東西

項目版本說明
Node.js22.13 以上（建議 22 LTS 並以 Volta 鎖定）04、08 用到 node:sqlite，需要 22.13+；其他專案 18/20 也可，但統一用 22 最省事。
Playwright 的 Chromium隨 Playwright 1.63.0大部分專案的 npm test 需要。在任一專案資料夾執行 npx playwright install chromium 一次即可。
Go（選用）1.24+只有要重新編譯 06 的 wasm / exe 時才需要；repo 已附 encdoc.wasm。
Rust（選用）stable + wasm32-unknown-unknown只有要重新編譯 09 的 wasm 時才需要；repo 已附 vr_core.wasm。

2. 確認 Node 正常

node -e "console.log('node-ok', process.version)"

預期印出 node-ok v22.x.x。若 errorlevel 為 -1073741819，是 Node 本身崩潰（執行環境問題），不是專案程式問題。

3. 一次驗證全部

雙擊根目錄 verify-all.bat（純 ASCII，會先 pushd "%~dp0"、印出路徑與 Node 版本，最後顯示 exit code 並 pause）。沒有 node_modules 的專案會自動 npm ci。也可以只跑部分專案：

node tools/verify-all.mjs --only 01,03
node tools/verify-all.mjs --install

預期最後出現 [verify-all] projects=14 failed=0 exit=0。紀錄寫到 %ProgramData%\NewMiscCode\verify-all\verify-all-YYYY-MM-DD.jsonl。

4. 單一專案

cd 03-duckdb-wasm-dashboard
npm ci
npm test

每個專案都有自己的 .bat 啟動檔（例如 start-windows.bat、run-tests.bat），細節見各自 README.html 的「快速開始」。

資料與 Log 位置

Windows 上所有專案預設寫到 %ProgramData%\NewMiscCode\<資料夾名稱>\（例如 C:\ProgramData\NewMiscCode\02-local-semantic-search）；Linux/macOS 寫在專案下的 ./data、./logs 或 ./output（已在 .gitignore）。每個專案都可用參數或環境變數改位置，名稱見各 README 的「除錯與日誌」。

Log 一律為 JSONL（一行一個 JSON，含 ts 與 level）。PowerShell 篩選範例：

Get-Content "$env:ProgramData\NewMiscCode\02-local-semantic-search\logs\*.jsonl" -Encoding UTF8 | ConvertFrom-Json | Where-Object level -eq 'error'

設計決策紀錄

記錄「為什麼這樣做」，避免接手者在不知道原因的情況下改回去。

決策原因影響
01 的 MCP 伺服器絕不寫 stdoutstdout 是 MCP 的通訊通道，任何 console.log 都會破壞協定診斷只寫 JSONL 檔與 stderr
02 中文關鍵字用「字元二元組」斷詞，不用 FTS5 trigram 或 jiebatrigram 查不到 2 個字的詞（實測「加密」查不到）；jieba 需要字典、對繁體較弱、多一個原生模組召回率高、會有雜訊命中；改斷詞要 --rebuild
02 開發時從第三方 npm 套件取得模型容器封鎖 HuggingFace；檔案以 SHA-256 核對與官方相同正式使用請走預設的 HuggingFace 官方來源
03 的 JSON 在 JavaScript 端解析新版 DuckDB-WASM 讀 JSON/Parquet 要線上下載擴充，離線與公司網路會失敗JSON 離線可用；Parquet 仍需連線
03 的 wasm 不進 git，06、09 的 wasm 進 git03 每個 30 MB 以上，可由 npm 重建；06 約 4 MB、09 約 0.3 MB，且重建需要 Go / Rust 工具鏈03 第一次要 npm run build
04、08、10 用 node:sqlite；02、07 用 better-sqlite3node:sqlite 免編譯原生模組（Windows 部署簡單），但需要較新的 Node；07 作者認為它在 Node 22 仍標示實驗性04/08/10 需要 Node 22.13+（10 為 22.5+）
根目錄 .gitattributes 對 testdata/、encoding-bad/ 設 -text這些是故意做壞的編碼範例，換行被 Git 正規化就失去測試意義commit 時已驗證位元組不變
.bat 純 ASCII，中文訊息放在 UTF-8 BOM 的 .ps1繁中 Windows 的 cmd 以 CP950 讀 .bat；Windows PowerShell 5.1 沒有 BOM 時會用 ANSI 讀 .ps1啟動鏈固定為 .bat → .ps1 → node

文件維護規範

  • 編碼：文字檔一律 UTF-8 無 BOM；.ps1 含中文時用 UTF-8 BOM；.bat 純 ASCII + CRLF（由 .gitattributes 強制）。
  • 寫法：文件以整份重建為主，不在舊內容上反覆局部追加；有歷史殘留就重寫。
  • 每個專案 README.html 必備分頁：概覽、快速開始（Windows / Linux）、使用說明、逐步驗證指南（含預期結果與截圖）、開發者指南（流程、模組、擴充方式、版本、變更紀錄）、除錯與日誌、限制與疑難排解、English。
  • 分頁內的小節要能用網址直接連到（例如 README.html#dev-add-action 會開啟該分頁並捲動到該處）。
  • 寫完一定要跑： 
    node tools/audit-text.mjs
node tools/check-docs.mjs
    兩個都要 0 問題。check-docs 會實際開瀏覽器檢查每個分頁、每個錨點、以及 390px 手機寬度不出現水平捲動。
  • 刻意做壞的範例檔只能放在名為 testdata 或 encoding-bad 的資料夾，稽核工具會略過，Git 也不會改動位元組。
  • 新增專案：資料夾命名 NN-名稱，verify-all 與 check-docs 會自動納入；記得在本頁各表格補一列。

English summary

Fourteen independent experiments, each with its own tabbed README.html (quick start, step-by-step verification guide, developer guide, debugging, limitations, English summary):

  1. 01 MCP server + CLI driving Playwright, red-box annotated screenshots and HTML reports.
  2. 02 Fully local hybrid search (SQLite FTS5 + sqlite-vec + multilingual-e5-small, RRF).
  3. 03 Zero-backend in-browser SQL analytics with DuckDB-WASM.
  4. 04 OpenTelemetry tracing across Node services with a home-made OTLP collector and waterfall viewer.
  5. 05 Yjs CRDT real-time collaboration with offline editing.
  6. 06 Text-encoding doctor (Go compiled to WebAssembly + native CLI).
  7. 07 Passkeys / WebAuthn with virtual-authenticator tests.
